项目概述与交付物

市场分析 · 需求分析 · 项目定位

金蝶发票云面向中小企业提供开票服务。原有形态是一套表单：用户自己判断税收分类编码、自己拆合并、 自己去电子税局跑一遍。WorkBuddy 把这套表单换成一个能对话的 Agent， 并在其下补齐了注册与账号管理的 H5 模块。项目交付 PRD、流程图、高保真原型与验收用例四类产出。

02

用户与真需求

用户研究 · Job-to-be-Done

用户要的不是「开票功能」，而是安全、省时、不出错地把一张合规发票交付给客户。 调研四类角色时，痛点被统一翻译成同一个问题：他在怕什么。 恐惧比需求稳定，也更能决定界面上该放什么。

四类角色 ×「怕什么」

角色画像情绪底层：怕什么 对应的设计动作
下游购方开票方的客户 怕发票开错（抬头 / 税号 / 品目），怕到账结算受影响 开票前生成校验快照，抬头库命中复用历史值
财务 / 开票专员出纳、会计、代账 怕税编选错被税务核查、怕手工开票耗时、怕限额超开被阻断后不知所措、怕专票开给个人违规 置信度分流 + 展示匹配依据（编码路径 + 规则来源）；风险预警不阻断但给出处置建议
财务主管财务经理 怕开票效率拖累回款、怕下属差错导致红冲率高、怕合规风险影响企业信用 红冲重开闭环 + 自进化看板（样本量 / 错因分布 / 版本对比）
管理层老板 / 总经理 怕税务处罚、怕经营数据失真、怕客户因开票慢流失 全程可解释 + 失败可恢复；台账可查询可对账

设计出发点：把产品设计从「功能优化」升级为「恐惧管理」—— 用 AI 把关 + 全程可解释 + 失败可恢复，逐条消除各角色的「怕」。这一条贯穿了后面所有界面决策。

03

业务流程设计

六步主链路 · 新用户首票分流

整条开票对话被拆成六个可观测的步骤。每一步都有明确的输入、输出与失败态， 失败不终止对话，而是降级到下一条可走的路。这是流程图贯穿始终的一条原则。

主链路

①
身份识别

锁定本单可开票税号；识别到 ≥2 个税号进入 MULTI_ACCOUNT 待选择。 后续所有步骤的取值范围都由此确定。

②
要素提取

解析买方信息与开票品目；支持文字、Excel、PDF 附件。数字类字段 OCR 准确率 ≥98%， 低置信度强制人工确认。抬头库目标命中率 ≥70%。

③
税编匹配 + 要素补全

逐行匹配税率与税收分类编码，按置信度分流，并展示匹配依据。纳税人资质决定动态税率。

④
合并拆分 + 规则校验

同税编可合并、不同税编提示拆分；六项规则校验 + 四组尾差公式，输出校验快照。

⑤
风险预警

5 类风险提示（限额、资质、抬头异常等），只提示不阻断，并给出可执行的处置建议。

⑥
开票执行

创建任务 → 轮询 5s / 超时 120s → 取版式文件 → 邮件或微信交付。防重复三原则 + 重试 5s/15s/30s。

↩
自进化闭环

用户在任一环节修改 AI 建议值，即写入 SelfEvolutionSample 并归入 5 类错因， 回流优化规则与模型。

新用户首票：为什么要做双路径分流

新用户流失几乎全部发生在「还没得到任何价值就被要求注册认证」这一步。 因此首票被拆成两条路：先把发票内容做出来，再谈注册。

路径 A 到电子税局导入开票

走完 ②~⑤ → 生成可导入的 Excel → 给出 4 步图文指引 → 用户在税局侧完成开具 → 再引导注册。 用户当天就能把票开出来，注册变成「下次更快」的理由而非门槛。

首步触达率目标≥95%
路径 B 直接注册通道

RPA 通道（税局账号密码 + 短信/扫码）或乐企联用通道（企业申请 + 授权）； 失败重试上限 3 次后转路径 A，不让用户卡死在注册页。

首票后注册转化率目标≥60%

两个独立子场景（复用同一匹配内核）

US-10
税编批量匹配

企业初次接入梳理历史税编、或按合同导出的待开票清单提前匹配。 粘贴表格或上传 Excel/CSV，两段式输出：≥0.9 自动通过段 + 待复核段。 解析能力完全复用 US-02，不重复建设。

US-09
发票查询助手

台账查询范围严格限定为用户有权访问的税号；红冲后状态同步展示（已红冲）。 查询偏好与使用量同时作为自进化特征。

04

三个关键产品决策

逻辑思维 · 取舍与权衡

作品集里最值得看的不是功能清单，而是在有约束时怎么选。 以下三个决策均经过取舍并落到了规格里。

决策一

置信度分流：把「AI 全自动」改成「三段式」

问题　税编选错的代价是税务核查，不是一次糟糕的交互。全自动省时但不可接受， 全人工准确但回到了原点。

决策　按置信度切三段，各段的界面语言完全不同：

状态置信度产品表现 颜色
AUTO_MATCHED≥ 0.90自动采用，静默展示，不打扰用户 绿
NEED_CONFIRM0.60 – 0.90 交用户决策，同时给出编码路径与规则来源作为判断依据 黄
NEED_MANUAL< 0.60转人工，不猜 红

结果指标　自动采用率 ≥70%、自动采用项税务复核准确率 ≥95%。 一屏之内颜色即可辨认待处理项。

决策二

匹配链路顺序：把 LLM 放到最后一档

问题　语义理解每次调用都在花 token，而大量开票项是重复的。

决策　四级降级链，越靠前越便宜：

S1 批量税编匹配库命中即用 S2 外部税编接口 piaozone3000ms 超时 / 不重试 / 连续失败 5 次熔断 S3 本地语义模型降级记录 source S4 综合置信度 → 分流

取舍　外部接口设 max_retry=0， 宁可立刻降级也不让用户等第二次超时——对话产品里，延迟本身就是一种失败。

结果指标　接口命中率 ≥60%、单位开票语义理解 token 下降 ≥50%，无效 token 消耗可统计。

决策三

风险预警不阻断开票

问题　限额超开、资质不符等 5 类风险，如果一律硬拦，用户会卡在一个自己无法解决的弹窗前 （这正是调研中「怕被阻断后不知所措」那一条）。

决策　规则校验（六项 + 四组尾差公式）是硬阻断，因为它决定税局是否驳回； 风险预警是软提示，因为它决定的是商业判断，应该交给人。每条预警都必须附带处置建议。

≤ 0.01单行金额尾差
≤ 0.01汇总金额尾差
≤ 0.06单行税额尾差
≤ 1.27汇总税额尾差

四组容差写进文档而不是留给开发猜，是因为这类数字一旦不一致， 测试与税局侧会出现互相矛盾的结论。

动线 1从 PC 端扫码到配置完成 5 屏 · 目标 5 分钟内完成

动线 2RPA 通道 · 税局登录与认证 3 屏 · 接口 B1 / B4 / B5

列表与详情共享同一套结构，字段顺序、状态标识、操作位置完全一致， 用户在两屏之间不需要重新建立认知。

动线 5未绑定用户的兜底引导 1 屏 · 承接「先开票、后注册」

这一屏是整个模块与 Agent 主链路的接缝：用户从对话里被带过来时， 必须先看到「为什么需要绑定」，再看到「怎么绑定」。顺序反了转化率就没了。

开票执行的三条防重复原则

  • 创建幂等　同一校验快照只允许产生一个 task_id。
  • 轮询有界　5s 间隔、≤120s 超时， 超时进入可恢复的重试态而非失败态。
  • 退避重试　5s / 15s / 30s 三次退避； 每次重试都复用原 task，不再新建。

07

数据指标与自进化飞轮

数据分析 · 对产品数据负责

这个产品的特殊之处在于：用户的每一次纠错都是训练数据。 「用户改了 AI 的建议值」被定义为一等公民事件， 落成 SelfEvolutionSample 与 5 类错因，形成闭环。

自进化飞轮

S1 采集用户在开票流程中修改 AI 建议值 → 实时写入 SelfEvolutionSample
S2 归因按 5 类错因分类：field_parse_error / semantic_error / context_insufficient / rule_missing / result_error
S3 批处理调度批量样本，产出规则补丁或模型迭代候选
S4 部署规则 / 模型上线，版本可对比
S5 观测回滚进化看板展示样本量、错因分布、版本对比；指标下降可回滚

分阶段策略：样本 <500 条为冷启动， 仅做规则补丁；≥500 条进入热运行阶段，开启组织级偏好与模型重训。 先定阈值再谈智能，是为了避免在数据不足时用噪声去改模型。

交互设计原则（约束下的设计）

WorkBuddy 平台只提供两种交互单元：结构化文字消息 与 2~4 个可点击选项按钮， 且是单 Agent 型专家、无跨 Agent 调度。这意味着所有分支必须压缩到 4 个选项以内， 复杂表单要拆成多轮对话。整套六步链路的节奏就是在这个约束下反推出来的—— 先确认技术边界，再设计交互，而不是反过来。

这个项目的核心判断是：B 端产品的难点其实是 C 端式的。 使用者不是专家，他在一个会被追责的场景里操作一个自己不完全理解的系统。 所以真正有效的设计不是把功能做全，而是让每一步都可解释、可退出、可恢复。
